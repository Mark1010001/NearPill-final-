# Packet 0 — `users` RLS / authentication-bootstrap characterization

**Status:** source-characterized, NP-031 **OPEN**; no live PostgreSQL security acceptance. 2026-10-31.

## Existing behavior observed (no migration applied)

The current source uses **one backend-owned identity and session system**, not Supabase Auth. The canonical Hono composition root wires `createPostgresIdentityRepository(pool)` and `createPostgresSecurityRepository(pool)` to the same PostgreSQL pool. The compatibility repository calls `BEGIN`, then transaction-local `set_config('app.user_id', ..., true)`, `app.role` and `app.capability`, and commits or rolls back before returning the connection.

| Existing operation | Code path | Transaction-local actor before `users` access | Required compatibility observation |
|---|---|---|---|
| Registration/OTP email uniqueness check | `identity-repository.js` `findIdByEmail` | `user_id=''`, role `anonymous`, capability `''` | `SELECT id FROM users WHERE email=$1` precedes verification and account creation |
| Login account lookup | `identity-repository.js` `findAuthUserByEmail` | `user_id=''`, role `anonymous`, capability `''` | `SELECT * FROM users WHERE email=$1` happens *before* password verification |
| Password-recovery lookup | `identity-repository.js` `findRecoveryAccountByEmail` | same anonymous context | `SELECT id,email FROM users WHERE email=$1` before proof of account ownership; public recovery responses must remain neutral |
| Legacy password-hash upgrade during login | `identity-repository.js` `replacePasswordIfCurrent` | same anonymous context | compare-and-swap `UPDATE users SET password=... WHERE id=... AND password=priorHash` occurs after password check but *before* request actor is installed; do not treat all anonymous password writes as safe |
| New customer registration | `identity-repository.js` `createCustomer` | same anonymous context | `INSERT INTO users` must work for approved registration without admitting arbitrary actor/role creation |
| Reset-link password change | `security-repository.js` `resetPasswordWithChallenge` | role `system`, capability `identity_security`, no user ID | `SELECT ... FOR UPDATE` validates challenge; `UPDATE users` and challenge consumption plus session/family revocation occur within one transaction |
| Backend session lookup | `security-repository.js` `findActiveSession` | role `system`, capability `identity_security`, no user ID | hashed-session query joins `users` **before** the validated session's actor ID/role is set; membership lookup follows that verification |
| Refresh-token validation and rotation | `security-repository.js` `rotateRefreshToken` | role `system`, capability `identity_security`, no user ID | hashed-refresh lookup joins `users` and locks session/family **before** credential validity is established; valid rotation consumes old token and creates new credentials, while replay revokes the family; missing token causes no write |
| Authenticated profile retrieval | `identity-repository.js` `findProfileById` | verified customer actor (`user_id=17`, role `customer` in synthetic fixture) | read filters on requested `users.id`, and transaction-local actor metadata is applied separately; a future RLS policy must deny cross-account profile access under the real app role |
| Authenticated profile update + reread | `identity-repository.js` `updateProfile` → `findProfileById` | verified customer actor in **both** successive transactions | phone/birthdate UPDATE and profile SELECT are two distinct transactions with the same verified actor; no guarantee of cross-account denial is established by the recording client |
| Admin pharmacy-membership list | `security-repository.js` `listDrugstoreMemberships` | verified admin actor and `identity_security` capability | `pharmacy_memberships` joins `users` to display partner names/emails, scoped to a pharmacy ID; future `users` RLS must preserve an authorized admin view without granting unrestricted customer access |
| Admin pharmacy-membership assignment | `security-repository.js` `upsertMembership` | verified admin actor and `identity_security` capability | `SELECT id,role FROM users` checks a target account is `partner` before inserting membership and audit event in one transaction; a non-partner target produces no write |

| Administrator order listing | `order-repository.js` `listAdminOrders` | verified admin actor, `order_mutation` capability | joins `orders` with `users` to project customer name/email for the admin portal; its broad read requires a tightly authorized admin policy and cannot be justified by the capability string alone |
| Administrator audit log | `report-repository.js` `listAuditLogs` | verified admin actor, no capability override | `LEFT JOIN users` exposes actor names/emails/roles in the bounded audit log; a restrictive `users` RLS policy may yield null user columns without separate approved access |
| Payment lookup authorization | `payment-subscription-repository.js` `findOrderPaymentForActor` | verified request actor, no capability override | checks own order ownership OR a `users.role='admin'` subquery; loss of visibility into the caller's own `users` row may deny legitimate admin payment views; do not broaden customer access to fix it |

These observations are recorded by `backend/test/packet0-users-auth-bootstrap-rls.test.mjs` against the actual repositories and a recording pool; they are not a substitute for the real PostgreSQL permission/role checks.

## Dependency and cleanup map for the eventual database packet

- **NP-031 remains a blocker.** The canonical `0001_core.sql` creates `users`; migrations `0001`–`0007` do not enable and force RLS on it. Never report the existing policy history as accepted or retrofit a historic migration in place.
- The current legacy-hash compare-and-swap runs with an **anonymous** request actor despite verified password material; broad anonymous `UPDATE users` grants would be unacceptable. The authorized database design must choose a narrow and auditable elevation/helper or a rigorously constrained operation before enforcing the new policy.
- Refresh rotation additionally joins `users` under `identity_security` before it knows whether the refresh token is valid; the reviewed policy must support single-use rotation, replay-family revocation and a no-write invalid-token path without exposing arbitrary user records.
- Administrator order/audit reporting also joins `users`, while payment actor checks use a role subquery. Their different context capabilities (`order_mutation` for admin orders, none for reporting/payment reads) must be considered in the eventual narrowly scoped RLS policy, together with real app-role negative tests.
- Privileged membership administration additionally joins/reads `users` to show partner assignments and enforce the *partner-only* membership condition. It requires a reviewed, narrowly authorized admin path under the actual non-bypass application role; neither the route's `auth: admin` declaration nor the transaction-local capability is an RLS policy by itself. The source test observes an audit insert for successful assignment and no insert for a non-partner; real DB authorization and cross-tenant negatives remain unverified.
- Ordinary customer profile reads and updates query `users` under a verified `customer` actor. Their id parameters are supplied by the backend, but actual cross-account denial is **not** provided by SQL string shape alone; a real app-role RLS negative test is required. The existing profile update and subsequent read are separate transactions, so this test is a compatibility observation, not an atomic update-and-read claim.
- The reset-link branch is a trusted backend `identity_security` capability transaction, **not** a customer RLS bypass or proof of any actual SQL grant. A future DB policy must preserve single-use token validation and revocation in one transaction.
- A naive `users.id = current_setting('app.user_id')` policy alone would deny required **pre-auth** lookup/registration and the **system-capability** session lookup. This is a compatibility constraint, not approval to grant anonymous unrestricted `users` SELECT/INSERT/UPDATE or to trust client-set actor values.
- A reviewed remedy must constrain *what* the backend can query or mutate during credential bootstrap, keep unverified users from selecting arbitrary private records, prevent role/self-escalation, preserve password-reset and role lookup semantics, and maintain backend-owned identity. The precise policy/grants or narrowly scoped trusted database function is **not selected here**.
- Inspect real `public` table grants, `users` ownership, `FORCE RLS`, all applicable `USING`/`WITH CHECK` paths, function ownership/`search_path`, and API exposure with the actual non-owner/non-superuser/non-`BYPASSRLS` application role. Require tenant and account positive/negative tests, including anonymous and system-capability paths.
- Reconcile reviewed migration checksums and backup/restore evidence on the **explicitly authorized NearPill Supabase staging project** before any SQL change or provider cutover. Do not use privileged `postgres`/`service_role` for ordinary Hono queries; no direct database or Supabase Data API authority in web/Flutter.

## Evidence and limits

`node --test backend/test/packet0-users-auth-bootstrap-rls.test.mjs` checks nineteen characterization cases covering the original bootstrap flows, pre-verification email uniqueness, legacy hash compare-and-swap, and reset-token session revocation; two failure-path tests verify rollback/release when verified-session membership resolution or password-reset session revocation fails, and three additional refresh cases cover successful rotation, family revocation on replay, and a missing-token no-write result; two additional tests characterize authenticated customer profile reads and update/reread actor context; three tests record admin membership listing, partner-only assignment with an audit event and a non-partner no-write result; three further tests cover admin order customer joins, audit-log user joins, and the payment administrator role subquery. These are recording-client sequencing checks, not real PostgreSQL transaction atomicity evidence. The general source-RLS preflight already rejects missing `users` forced RLS in `packet0-db-live-connection-preflight.test.mjs`. All live grants, RLS isolation, migration replay, concurrency, payment reconciliation and restore tests remain **NOT RUN** without an authorized staging target. This document is a characterization/cleanup map for Packet 0, not a Packet 3/4 implementation or a release approval.
