# NearPill data and order inventory

Originally updated 17 October 2026; **cart/order paths and storage scope revalidated against the 31 October 2026 source snapshot** (static evidence, not a Flutter runtime or production database check). Scope: Flutter customer app, web operations portal, Node/PostgreSQL backend. Provider-backed payment architecture is implemented, but live payment collection remains disabled until an approved provider and policy are configured. Contact supplied by the team: **nearpillemail@gmail.com**. The legal operator name, address and production hosting are unconfirmed.

Real medicine transactions remain blocked pending approved database policy and staging negative tests. |

A local status cannot confirm money movement; provider/reconciliation evidence is required. |

| Operational records | User ID, action, descriptions and timestamps; audit changes | PostgreSQL `audit_logs`; backend operators / authorized APIs | Migration and backend. Database, audit, backup and provider-log retention periods are not configured. Mobile debug HTTP logging omits bodies and headers; existing operational logs still need review. |

**Order outcomes:** order transitions are centralized and reservation release/fulfilment is idempotent. A confirmed payment cannot become `refunded` from an order-status mutation. Cancellation requiring money movement remains `cancellation_pending`/`refund_pending` until provider or approved reconciliation evidence confirms the refund. Commercial cancellation/refund rules still require owner approval before live payments.

**Claims:** public medicine/pharmacy records now require backend publication/verification state. Legacy records are not auto-published, fabricated licence/rating fixture claims are removed, and remaining browser branch fixtures are explicitly synthetic. No actual pharmacy licence, medicine registration, image licence or business registration is asserted merely because a fixture exists.

**Retention and rights:** no automatic business-record deletion schedule is approved. Mobile credentials persist until cleared/expired/revoked; server session/challenge state is durable and expiring in PostgreSQL. Browser display state is not an authorization source. Contact the supplied email for requests; identity checks, request handling and approved retention periods still need an operational procedure. See the [audit](readiness-audit.md) and [shared prelaunch policies](../web/public/policies.json).
